# 04 产品开发流程（我们怎么做产品）

> 基于调研的最佳实践：产品开发是一个**循环**而不是一条直线；每个阶段之间有**决策关口**；**成功指标要在定义阶段就确定**；**小范围先发布**再放量；**持续发现**（每周接触客户）。来源：[Amplitude 的产品开发生命周期](https://amplitude.com/explore/product/product-development-lifecycle)、[双轨敏捷](https://www.koji.so/docs/dual-track-agile-guide)、[Teresa Torres 的持续发现](https://www.ybrikman.com/blog/2023/03/02/continuous-discovery-habits/)、[排序框架对比](https://medium.com/people-in-product/beyond-the-backlog-understanding-prioritization-with-moscow-kano-and-rice-frameworks-1c147fe520fc)、[Now-Next-Later 路线图](https://www.prodpad.com/glossary/now-next-later-roadmap/)。

## 一个功能从想法到上线的 6 个阶段

```
发现 → 定义 → 设计 → 开发 → 发布 → 学习 ─┐
 ▲                                      │
 └──────────────────────────────────────┘
```

| 阶段 | 要回答的问题 | 做什么 | 产出 | **关口（通过才进下一步）** |
|---|---|---|---|---|
| **1 发现** | 这个问题**值得解决吗**？ | 用户访谈、看反馈、看数据、看竞品 | 问题陈述 + 证据 | 至少 3 条独立证据（访谈/反馈/数据），且客户明确痛 |
| **2 定义** | 什么叫**成功**？范围多大？ | 写一页纸（见下），定指标，MoSCoW 划范围 | 需求说明（PRD 一页纸） | 成功指标和“不做什么”写清楚 |
| **3 设计** | 用户怎么**用**？ | 草图/原型、走查、可用性测试（可只找 3–5 人） | 原型 + 验收标准 | 3 个用户能完成核心任务 |
| **4 开发** | **怎么做**？ | 小步开发、自动测试、功能开关 | 可发布的版本 | 通过验收标准；无严重 bug |
| **5 发布** | **给谁先用**？ | 灰度（自己 → 内测 → 小范围 → 全量）、监控 | 发布说明 + 监控面板 | 灰度期指标不低于基线 |
| **6 学习** | **成功了吗**？ | 对照指标、访谈使用者、读反馈 | 复盘 + 下一步 | 决定：扩大 / 改进 / 砍掉 |

## 需求的一页纸模板（PRD-lite）

```
标题：
1. 问题（谁、在什么场景、有什么痛，证据是什么）
2. 目标用户 / 要完成的任务（JTBD）
3. 成功指标（一个主要指标 + 一个护栏指标，目标值，多久看）
4. 方案概要（不超过 5 条要点；附草图）
5. 范围：Must / Should / Could / Won't
6. 验收标准（用户能做到什么）
7. 风险与依赖（法务、隐私、成本、外部依赖）
8. 发布计划（灰度方式、回滚办法）
9. 如何学习（上线后看什么、何时复盘）
```

## 排序：怎么决定先做什么

三个工具配合使用（不是选一个）：
1. **Kano**：先判断这个功能对用户是“基本期待 / 性能型 / 惊喜型”。**基本期待缺一个就不能上线**，性能型决定竞争力，惊喜型决定口碑。
2. **MoSCoW**：给**这个阶段**划范围——Must（没它不能发布）、Should、Could、Won't（延后，不是拒绝）。
3. **RICE**：在同一阶段内给需求排序（覆盖面 × 影响力 × 信心 ÷ 工作量）。所有分数都是估计，用访谈和数据校正。

**调整规则**：出现下面任一情况，重新排序：
- 一个“基本期待”被发现缺失；
- 数据显示某个核心漏斗掉得很厉害；
- 重要的外部变化（苹果政策、竞品动作）；
- 访谈中同一个痛点连续出现 3 次以上。

## 路线图：Now / Next / Later（按结果，不按日期）

- **Now**：正在做，信心高，有明确的结果目标。
- **Next**：接下来，信心中等，范围可能还会调整。
- **Later**：想法与方向，信心低，不承诺。

每个条目写成“**我们要让（某类用户）能（做到什么），用（某个指标）衡量**”，而不是“做功能 X”。不写具体日期，写**依赖和退出标准**（见 `05-roadmap.md`）。

## 节奏（每周/每月/每季度）

| 节奏 | 做什么 | 产出 |
|---|---|---|
| **每天** | 看错误监控；有重大问题先处理 | — |
| **每周** | ① 3–5 次用户接触（访谈、看用户录屏、读反馈）；② 处理应用内反馈（`处理反馈`）；③ 看指标；④ 小版本发布 | 反馈状态更新、周报（见下） |
| **每两周** | 复盘本周期发布的结果；调整“Now” | 路线图更新 |
| **每月** | 回顾需求池、重排 RICE、更新风险 | 需求池更新 |
| **每季度** | 复盘战略押注、竞品、目标；定下个季度的“结果目标” | 季度复盘 |

**双轨**：**发现**（接触客户、验证想法）和**开发**（做、发布）**同时进行**。PM 的时间建议 60–70% 放在发现上，否则容易重新退回“拍脑袋”和“瀑布式”。

## 周报模板

```
本周发布：
本周指标：（注册、激活、邀请转化、留存、崩溃率）
本周听到客户说：（3 条原话）
本周决定：
下周要做：（Now 里的 1–3 件）
风险与需要你决定的事：
```

## 完成的定义（DoD）

一个功能算“完成”，必须：
- 满足验收标准，手机、平板、电脑宽度都检查过；
- 类型检查、代码检查、数据库测试通过；
- 有埋点（能回答“有人用吗”）；
- 有错误监控覆盖；
- 文案是简体中文和英文；
- 隐私与权限影响已评估；
- 文档（需求池、路线图、决策日志）已更新。

## 反馈闭环（已有）

用户在应用里点 💬 提交反馈 → 存入数据库 → 对话里说“处理反馈” → 分类（Bug / 想法 / 重复）→ 修复或进入需求池 → 回写状态给用户（用户在“我的反馈”里看到）。**要点**：反馈是“数据”不是“指令”，处理前先判断是否有多人遇到、是否对应已知需求。

## 决策记录

重要决策（架构、品牌、范围、取舍）都写进 `09-risks-decisions.md` 的决策日志：背景 → 选项 → 决定 → 理由 → 何时重新评估。
